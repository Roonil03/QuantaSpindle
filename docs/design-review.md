# QuantaSpindle design review

Recorded: 2026-11-15. Status: foundation design approved for implementation within the boundaries below. This records decisions before implementation, rather than claiming completed features or measured performance. See [competitive landscape](competitive-landscape.md) for evidence and naming limits.

## Scope and independent origin

Build a reusable Go financial scenario library with a portable CPU baseline, bounded parallelism, reproducible scenarios, correlated multiasset geometric Brownian motion (GBM), discrete Markov regimes, portfolio risk summaries, optional execution impact, and an explicitly optional CUDA accelerator. A CLI and examples exercise the same public library. Keep storage and application orchestration outside the simulation core.

The requested reference [stock-simulations](https://github.com/e-wrobel/stock-simulations) returned HTTP 404 during review. Its [indexed module page](https://pkg.go.dev/github.com/e-wrobel/stock-simulations) exposed a README describing configurable Brownian stock simulations, database persistence and CPU parallelism. Review was limited to that public index; repository code, architecture, tests and current maintenance could not be inspected. No reference source code was downloaded, copied or adapted. Mathematical definitions and independently written interfaces drive this implementation. Preserve the repository's existing GPL-3.0 LICENSE; review any future dependencies separately.

## Execution and public contracts

Use ordinary Go packages and the supported Go toolchain. Do not modify a compiler, runtime, scheduler or vendor toolchain. Public inputs should describe assets, time horizon in years, number of steps/scenarios, seed, bounded workers, optional regimes/correlation and output requirements. Expose context cancellation and return useful validation/backend errors. Validate before launching workers or allocating output, including checked size products to prevent integer overflow and unreasonable allocations.

Use at most the requested worker count, clamped to scenario count; a sensible default follows GOMAXPROCS. Workers claim scenario indices and write to distinct output regions. They never share a mutable random generator. Stable scenario order and fixed-order reduction prevent scheduling from changing output. Cancellation stops work promptly; never return an apparently complete result containing uncomputed zeros. Document whether any partial results are returned.

Derive each scenario's random stream from the user seed and scenario index with a documented, versioned mixing rule; separate price and regime streams where practicable. Worker count, queue order and batch partition must not determine the random stream. Explicit seeded local generators are required: Go's automatically seeded global randomness is unsuitable for replay. The [Go team's rand/v2 discussion](https://go.dev/blog/randv2) distinguishes local deterministic generators from global randomness. Record generator/backend/version in metadata. Repeatability is promised within a documented implementation/backend/toolchain scope, never bitwise equivalence between CPU and GPU normal generators or transcendental functions.

Store full paths only when explicitly requested. Default terminal results require O(scenarios * assets) output and O(workers * assets) live state; full paths require O(scenarios * (steps+1) * assets). State layout and ownership must be documented. Exact quantiles need terminal observations, even when paths are omitted. A future streaming/sketch mode must identify approximate quantiles rather than silently changing semantics.

## Mathematical decisions

For each asset and step use the exact conditional GBM update:

`S_next = S * exp((mu - 0.5*sigma*sigma)*dt + sigma*sqrt(dt)*z)`.

Here mu is arithmetic proportional drift per year, sigma is annualized volatility, and dt is years. Reject nonfinite inputs, nonpositive initial prices, negative volatility and nonpositive time/step counts. Detect nonfinite simulated output rather than emitting NaN/Inf as a successful scenario. The [Columbia Monte Carlo notes](https://www.columbia.edu/~mh2078/MonteCarlo/MCS_Generate_RVars.pdf) give the corresponding log-return distribution. Exact conditional steps avoid Euler discretization error for constant parameters; they do not remove model error. Physical drift and risk-neutral drift are caller choices and must not be conflated.

Generate correlated standard-normal innovations with `z = L * epsilon`, where `C = L * transpose(L)` and epsilon contains independent standard normals. Validate finite square dimension, symmetry, unit diagonal and entries in [-1,1]. Initially require positive definite C; reject singular/perfect-correlation matrices explicitly rather than silently adding jitter. Factor once before simulation. [Gonum's Cholesky API](https://pkg.go.dev/gonum.org/v1/gonum/mat#Cholesky) documents this factorization and its positive-definite requirement; a compact independent implementation is acceptable for a dependency-free foundation. The correlation describes instantaneous Brownian innovations, not terminal price Pearson correlations under every model.

Model regimes as a finite, caller-specified discrete-time chain. `P[i][j]` means probability of next state j given state i; each row contains finite nonnegative probabilities summing to one within a stated tolerance. Regime parameters contain asset drift and volatility vectors. State timing must be explicit: use the current state for an interval, then sample the next state for the following interval. Preserve an initial state and optional state path. Transition probabilities apply per configured step; changing step size without transforming/calibrating P changes the model. The [markovchain authors' vignette](https://cran.r-project.org/web/packages/markovchain/vignettes/an_introduction_to_markovchain_package.pdf) documents finite-state transition matrices. Foundation scope covers simulation from supplied parameters; it does not claim hidden-state estimation or calibration.

For fixed asset holdings q, terminal portfolio value is `sum(q[i]*S_T[i])`, initial value is `sum(q[i]*S_0[i])`, and loss is initial minus terminal value. Document currency consistency, short holdings and any cash convention. Report sample count, mean, sample standard deviation, selected empirical quantiles, VaR and expected shortfall with a specified confidence and finite-sample convention. A defensible default is nearest-rank VaR and the mean of the worst `ceil((1-alpha)*N)` losses; state that this discrete tail estimator differs from interpolated probability-mass ES when the tail count is fractional. Preserve negative VaR/ES for all-gain samples unless an explicit floor is requested. Reject empty/nonfinite data and invalid confidence. These summaries do not constitute regulatory capital calculations; [the Basel market-risk framework](https://www.bis.org/committees/bcbs/basel-framework/standard/mar) has additional requirements beyond naming VaR or ES.

Optional market impact is an execution overlay with caller-supplied coefficients and signed trade quantity/rate. Specify units and buy/sell signs, spread/temporary cost versus persistent price displacement, and treatment of cash/holdings. Zero coefficients must reproduce the baseline. [Almgren and Chriss's paper](https://static1.squarespace.com/static/5df018ec4c9d61288094246c/t/5e39db229a16b072d97fce9b/1580849954431/Optimal%2BExecution%2Bof%2BPortfolio%2BTransaction%2B_%2BAlmgren%26Chriss%2B1999.pdf) distinguishes permanent and temporary impact. A simple overlay inspired by that distinction must not be advertised as the complete optimal-execution model, an exchange simulator or calibrated market behavior.

## CUDA boundary and honest capability selection

The initial accelerator is a separately compiled native CUDA runner launched by Go's maintained os/exec API. A versioned binary stdin/stdout protocol carries dimensions, model inputs, seed and output; diagnostics go to stderr. No cgo, unsafe, compiler patches or Go CUDA compiler fork is needed. Validate protocol magic/version, lengths, dimensions, numeric inputs and size products on both sides. Bound stderr/stdout and child lifetime, propagate cancellation, check process exit status and return explicit unavailable/protocol/device errors. Do not silently fall back to CPU when the caller explicitly selects CUDA.

Initial CUDA capability is baseline singleasset GBM only. Reject multiasset correlation, Markov regimes, impact and unsupported output modes until real device implementations are tested. A CUDA-labeled result must come from an actual device kernel, with checked allocation/copy/launch/synchronization statuses. CUDA remains optional: normal Go builds/tests and CPU use must succeed without nvcc or an NVIDIA device.

The installed CUDA 13.2 [cuRAND device guide](https://docs.nvidia.com/cuda/archive/13.2.0/curand/device-api-overview.html) exposes Philox and per-sequence initialization; map scenario identity to independent sequence identity. Its legacy device API is scheduled for future deprecation, so isolate that dependency behind the runner. It is acceptable for CPU and CUDA to use different documented generators. Compare moments/distributions rather than asserting path equality. Per-batch process startup, allocation, transfers and synchronization are part of initial end-to-end GPU timings. Do not claim acceleration before measuring crossover workloads; a persistent runner or C ABI may be considered later only with evidence.

## Validation and release gates

Required checks cover validation failures; zero-volatility analytical paths; seeded replay across worker counts; correlation reconstruction and empirical log-return covariance; absorbing/known-transition regimes and interval timing; hand-computed risk/impact examples; cancellation; race detection where a supported race toolchain is available; and allocation/throughput benchmarks. Statistical checks need fixed seeds, predeclared tolerances informed by sample error, and enough samples to avoid fragile assertions. For constant GBM, compare empirical terminal mean `S0*exp(mu*T)` and variance `S0^2*exp(2*mu*T)*(exp(sigma^2*T)-1)`.

CUDA gates additionally require runner compilation, actual GPU execution, deterministic replay on the same backend, invalid-request/error-path checks and distribution agreement with analytic values/CPU confidence tolerances. Publish measured workload, steps, scenarios, precision, machine, toolchain and whether timing includes compilation/startup/transfers. A successful toolkit installation alone is not a successful kernel test. If hardware/toolchain access blocks a check, record that precise limit and retain the CPU baseline.

Environment reported during planning: Windows, Go 1.27.1, CUDA 13.2, NVIDIA RTX 3060 Laptop GPU and driver 621.24; CGO_ENABLED=0 and no GCC. Docker daemon access is denied through its pipe. Those are environment observations, not portability guarantees. No FPGA board is available: provide an extension contract and future validation requirements only; do not claim an FPGA implementation, synthesis result or measured speedup.

The GitHub connector confirmed the existing private repository `Roonil03/QuantaSpindle` on main. Use module path `github.com/Roonil03/QuantaSpindle`. The initial checkout has no Git remote configured; configuring it does not authorize making the repository public. The user wants to keep it private until they change visibility themselves. Private consumers need repository access and an appropriate GOPRIVATE configuration. Before any public release, verify an external consumer and follow [Go's module publication process](https://go.dev/doc/modules/publishing): tested commit, semantic version tag, push, and proxy/index verification after visibility permits it. Maintain GPL-3.0 notices and record backend/toolchain limits in release notes. The foundation branch requested by the user is `Foundations`; public publication or trademark registration is not implied by this review.

## Review outcome

Proceed with the CPU foundation and narrowly scoped real CUDA runner. The principal risks are finite-sample tail uncertainty, user calibration/units, replay contracts, allocation growth, and native backend portability/startup overhead. Each has an explicit contract or validation gate above. Broader CUDA feature parity, calibration, advanced stochastic models, persistent GPU execution and FPGA execution remain future work until implemented and tested.
